# 코덱스 교차 검증

같은 모델이 자기 글을 검토하면 오류가 잘 안 보입니다. 무엇을 의도했는지 알기 때문에 쓰인 대로가 아니라 의도한 대로 읽습니다. 그래서 **다른 회사 모델**에게, **문맥을 지우고** 검증을 맡깁니다.

검증자는 OpenAI 코덱스(`codex` CLI)입니다. 사용자의 ChatGPT 구독으로 돕니다.

## 먼저 확인

```bash
codex login status
```

- `Not logged in` 이거나 명령이 없으면: **그 사실을 사용자에게 말하고 멈추세요.** 설치는 `npm install -g @openai/codex`, 로그인은 `codex login` 입니다. 검증한 척하지 마세요.
- 로그인돼 있으면 진행합니다.

## 1. 검증자에게 줄 것을 챙긴다

세 가지만 줍니다.

| 준다 | 주지 않는다 |
|---|---|
| 사용자의 원래 요청 | 어떻게 만들었는지에 대한 설명 |
| 내가 내놓은 답 | 사용자가 무엇을 원했는지에 대한 해석 |
| 만든 파일의 **경로** | "이 부분이 걱정된다" 같은 힌트 |

과정을 알려주면 검증자가 그 과정을 따라 읽습니다. 그러면 문맥을 분리한 의미가 없습니다.

**파일은 내용이 아니라 경로를 주세요.** 검증자가 직접 열어보게 합니다. 같은 폴더의 원본 양식·출처대장도 스스로 찾아 읽습니다.

## 2. 부른다

프롬프트를 파일에 쓰고 stdin 으로 넘깁니다. 본문이 길어 인자로 넣기 어렵기 때문입니다.

```bash
codex exec \
  --sandbox read-only \
  --cd <작업 폴더> \
  --skip-git-repo-check \
  --ephemeral \
  --color never \
  --output-last-message /tmp/verdict.txt \
  < /tmp/verify-prompt.txt
```

각 플래그의 이유:

- `--sandbox read-only` — 검증자는 지적만 합니다. 파일을 고치는 것은 내 일입니다.
- `--ephemeral` — 기록을 남기지 않습니다. 매번 백지에서 시작해야 눈이 무뎌지지 않습니다.
- `--output-last-message` — 최종 판정만 파일로 받습니다. stdout 의 진행 로그는 버립니다.
- `--cd` — 작업 폴더. 이 안의 파일을 읽을 수 있습니다.

응답은 몇 분 걸릴 수 있습니다. 진행 상황을 사용자에게 한 줄로 알리세요.

## 3. 검증자에게 주는 프롬프트

`references/prompt.md` 의 틀을 그대로 쓰세요. 요약하거나 각색하지 마세요.

## 4. 판정을 받으면 — 여기가 가장 중요합니다

**검증자도 틀립니다.** 지적을 받았다고 바로 고치지 마세요. 순서를 지키세요.

1. **원본을 다시 확인합니다.** 파일을 열고, 출처대장을 보고, 계산을 다시 합니다.
2. 확인 결과 **내가 틀렸으면** 고치고, 무엇을 왜 고쳤는지 한 줄로 말합니다.
3. 확인 결과 **검증자가 틀렸으면 근거를 대고 반박합니다.** "원본 3쪽에 12억 4천만 원으로 되어 있고 출처대장도 같습니다. 이 지적은 맞지 않습니다."
4. **판단이 안 서면** 무엇이 불확실한지 말합니다. 추측으로 동의하지 마세요.

3번이 어색하게 느껴져도 그게 맞습니다. 사용자가 원하는 것은 동의가 아니라 정확한 문서입니다. 지적받았다는 이유만으로 멀쩡한 내용을 고치면, 그다음부터 이 검증은 아무도 믿지 않습니다.

**인용 없는 지적은 무시해도 됩니다.** 검증자 지침에서 인용을 요구했으므로, 위치와 원문 없이 온 지적은 지침을 어긴 것입니다.

## 5. 합의될 때까지 — 다만 끝은 있게

고쳤으면 **다시 검증받으세요.** 고쳤다는 내 말이 맞는지 아무도 확인하지 않으면 검증이 반쪽입니다.

2회차부터는 지난 라운드의 지적과 내 답을 프롬프트에 함께 넣어, 그 지적이 해결됐는지 판단하게 합니다.

멈추는 조건은 셋입니다.

| 조건 | 그때 할 일 |
|---|---|
| 검증자가 "문제 없음" | 합의. 결과를 보고하고 끝냅니다 |
| **같은 지적을 되풀이함** | 평행선입니다. 더 돌지 말고 사용자에게 양쪽 주장을 정리해 올리세요 |
| **4회차 도달** | 마찬가지로 사용자에게 판단을 넘깁니다 |

평행선일 때 억지로 합의하지 마세요. **판정하지 못했다고 말하는 편이 판정한 척하는 것보다 낫습니다.**

## 6. 사용자에게 보고할 때

고친 것만 말하면 사용자는 이 검증이 실제로 무엇을 걸렀는지 알 수 없습니다. 셋 다 말하세요.

- 무엇을 지적받았고
- 무엇을 고쳤고
- **무엇을 안 고쳤고 왜 안 고쳤는지**

```
코덱스 검증 결과 (2회 왕복, 합의)

· [불일치] 2쪽 "점검일 8월 12일" → 원본 확인 결과 8월 5일이 맞아 고쳤습니다.
· [근거 없음] 3쪽 "예산 3억" → 출처대장에 근거가 있어 반박했고, 코덱스가 수긍했습니다.
· 나머지 확인됨 14건.
```

## 검증이 강해지는 조건

검증자는 **파일로 남은 것만** 볼 수 있습니다. 대화로만 오간 정보는 대조할 방법이 없습니다.

- **출처대장이 있으면** 본문의 숫자를 그 표와 대조합니다. 가장 확실한 검증입니다 (`docflow` 스킬이 이 표를 만듭니다)
- **`.hwpx` 는 압축된 XML 이라 검증자가 못 읽습니다.** 같은 이름의 `.md` 초안이나 `.pdf` 를 함께 남기고, 그 경로를 주세요
- 출처대장이 없으면 내적 모순·계산 오류·요청과의 불일치까지만 잡힙니다. 그것도 값어치가 있지만, 사실 검증은 아닙니다
